# Отчёт: прогнозирование оттока абонентов телеком-оператора

## 1. Название и цель проекта

**Название:** прогнозирование оттока абонентов телеком-оператора.

**Цель:** построить и сравнить несколько классических моделей бинарной
классификации, выбрать лучшую модель по выбранным метрикам и объяснить, какие
факторы сильнее всего связаны с оттоком.

Задача важна для оператора связи: если модель заранее находит клиентов с
высоким риском ухода, отдел удержания может предложить им персональные условия.

## 2. Датасет

Использован файл:

```text
project/data/Customer Churn.csv
```

Датасет обезличен: в нём нет ФИО, телефонов, адресов, email или других прямых
персональных идентификаторов. Каждая строка описывает агрегированные показатели
поведения абонента.

Исходный размер: **3150 строк и 14 колонок**. Целевая переменная — `Churn`.
В коде имена колонок приведены к `snake_case`, поэтому target используется как
`churn`, но в исходном CSV он называется именно `Churn`.

После удаления 300 exact-дубликатов для моделирования осталось **2850 строк**:
13 признаков и 1 целевая переменная.

## 3. Первичный анализ данных

### 3.1. Качество данных

| Проверка | Результат |
|---|---:|
| Raw rows | 3150 |
| Raw columns | 14 |
| Пропуски | 0 |
| Exact-дубликаты | 300 |
| Rows после удаления дублей | 2850 |
| Columns после удаления дублей | 14 |

Дубликаты удалены до train/test split, чтобы одинаковые записи не попали
одновременно в обучение и тест.

### 3.2. Баланс классов

| Churn | Количество | Доля |
|---:|---:|---:|
| 0 | 2404 | 84.35% |
| 1 | 446 | 15.65% |

Есть заметный дисбаланс классов: ушедших клиентов примерно в 5.4 раза меньше,
чем оставшихся. Поэтому accuracy недостаточна как главная метрика:
`DummyClassifier`, который всегда предсказывает класс 0, получает accuracy
0.8439, но recall, F1 и ROC-AUC для поиска оттока фактически бесполезны.

### 3.3. Описание признаков

| Группа | Признаки |
|---|---|
| Активность клиента | `seconds_of_use`, `frequency_of_use`, `frequency_of_sms`, `distinct_called_numbers` |
| Качество связи | `call_failures` |
| Жалобы | `complaints` |
| Подписка и тариф | `subscription_length`, `charge_amount`, `tariff_plan`, `status` |
| Демография | `age_group`, `age` |
| Экономическая ценность | `customer_value` |

В данных нет явного идентификатора клиента. Признак `status` входит в исходный
датасет, используется как категориальный и связан с целевой переменной.

### 3.4. Базовые наблюдения EDA

Наиболее сильные связи с `Churn` по корреляции и важности моделей:

- `complaints`: наличие жалоб резко повышает вероятность оттока;
- `status`: неактивный статус связан с уходом;
- `seconds_of_use`, `frequency_of_use`, `frequency_of_sms`,
  `distinct_called_numbers`: меньшая активность связана с более высоким риском;
- `customer_value`: клиенты с меньшей ценностью чаще уходят;
- `subscription_length` и `call_failures` входят в топ важностей boosting-модели.

Графики сохранены в `artifacts/figures/`: распределение target,
корреляционная матрица, распределения числовых признаков и сравнение признаков
по классам `Churn = 0` и `Churn = 1`.

## 4. Подготовка данных и протокол

- Разделение: train/test = 80/20.
- Стратификация по `Churn`.
- `random_state=42`.
- Cross-validation: `StratifiedKFold(n_splits=5, shuffle=True, random_state=42)`.
- Числовые признаки масштабируются через `StandardScaler`.
- Категориальные/бинарные признаки `complaints`, `tariff_plan`, `status`,
  `age_group` кодируются через `OneHotEncoder(handle_unknown="ignore")`.
- Все преобразования входят в sklearn `Pipeline`, поэтому тот же pipeline
  используется в обучении, тесте и API.

## 5. Модели

Обязательный baseline:

- `DummyClassifier(strategy="most_frequent")`.

Классические модели:

- `LogisticRegression`;
- `DecisionTreeClassifier`;
- `RandomForestClassifier`;
- `GradientBoostingClassifier`;
- `KNeighborsClassifier`.

Для `LogisticRegression`, `DecisionTreeClassifier` и
`RandomForestClassifier` использован `class_weight="balanced"`, чтобы частично
скомпенсировать дисбаланс классов. Для `GradientBoostingClassifier` и KNN
оставлены стандартные sklearn-настройки, кроме зафиксированного `random_state`
там, где он доступен.

### 6.1. Cross-validation на train

|---|---:|---:|---:|---:|---:|---:|
| GradientBoostingClassifier | 0.9430 | 0.8798 | 0.7364 | 0.8012 | 0.9776 | 0.9153 |
| KNeighborsClassifier | 0.9294 | 0.8593 | 0.6581 | 0.7444 | 0.9630 | 0.7918 |
| RandomForestClassifier | 0.8939 | 0.6031 | 0.9411 | 0.7351 | 0.9710 | 0.7777 |
| DecisionTreeClassifier | 0.8601 | 0.5344 | 0.8738 | 0.6628 | 0.9312 | 0.6820 |
| LogisticRegression | 0.8425 | 0.4987 | 0.8739 | 0.6347 | 0.9351 | 0.6345 |
| DummyClassifier | 0.8434 | 0.0000 | 0.0000 | 0.0000 | 0.5000 | 0.0000 |

### 6.2. Test set

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC | Confusion matrix [[TN, FP], [FN, TP]] |
|---|---:|---:|---:|---:|---:|---|
| GradientBoostingClassifier | 0.9526 | 0.9306 | 0.7528 | 0.8323 | 0.9818 | [[476, 5], [22, 67]] |
| KNeighborsClassifier | 0.9351 | 0.8333 | 0.7303 | 0.7784 | 0.9686 | [[468, 13], [24, 65]] |
| RandomForestClassifier | 0.8789 | 0.5694 | 0.9213 | 0.7039 | 0.9690 | [[419, 62], [7, 82]] |
| DecisionTreeClassifier | 0.8596 | 0.5306 | 0.8764 | 0.6610 | 0.9219 | [[412, 69], [11, 78]] |
| LogisticRegression | 0.8368 | 0.4877 | 0.8876 | 0.6295 | 0.9288 | [[398, 83], [10, 79]] |
| DummyClassifier | 0.8439 | 0.0000 | 0.0000 | 0.0000 | 0.5000 | [[481, 0], [89, 0]] |

Baseline `DummyClassifier` показывает accuracy 0.8439 только из-за дисбаланса,
но он не находит ни одного ушедшего клиента: recall 0.0000, F1 0.0000,
ROC-AUC 0.5000. Все осмысленные модели существенно лучше baseline по F1 и
ROC-AUC.

Лучшая модель по test F1: **GradientBoostingClassifier**.

Лучшая модель по test ROC-AUC: **GradientBoostingClassifier**.

RandomForest даёт самый высокий recall на test (0.9213), но при этом делает
много ложных тревог: precision 0.5694 и 62 false positives. Для задачи
удержания это может быть приемлемо, если компания готова часто обращаться к
клиентам без реального риска ухода. В текущей постановке выбран баланс F1 +
ROC-AUC, поэтому GradientBoosting лучше.

## 7. Оценка обобщающей способности

У `DecisionTreeClassifier` train F1 равен 0.6820, CV F1 — 0.6628. Близкие
значения получены при ограниченной глубине и минимальном размере листа.

У `RandomForestClassifier` train F1 равен 0.7777, CV F1 — 0.7351, test F1 —
0.7039. Высокий recall достигается при большем числе положительных прогнозов.

У `GradientBoostingClassifier` train F1 0.9153 против CV F1 0.8012. Разрыв
между оценками сопровождается test F1 0.8323 и test ROC-AUC 0.9818 — лучшими
результатами среди рассмотренных конфигураций.

## 9. Выбор лучшей модели

Выбрана модель **GradientBoostingClassifier**.

Обоснование:

- лучший test F1: 0.8323;
- лучший test ROC-AUC: 0.9818;
- precision 0.9306, то есть модель редко помечает стабильных клиентов как
  уходящих;
- recall 0.7528, модель находит около 75% ушедших клиентов на test set;
- результат существенно лучше baseline: F1 вырос с 0.0000 до 0.8323,
  ROC-AUC с 0.5000 до 0.9818;
- модель подходит датасету, потому что данные табличные, все признаки числовые
  или низкокардинальные категориальные, а градиентный бустинг хорошо ловит
  нелинейные зависимости и взаимодействия без усложнения стека.

## 10. Сервис, интерфейсы и воспроизводимость

Проект упакован как воспроизводимый ML-сервис:

- `src.models.train` обучает модели, сохраняет `best_model.joblib`, metadata,
  таблицы метрик и графики;
- `src.models.predict.ChurnModel` загружает сохранённый sklearn pipeline и
  возвращает вероятность оттока, бинарный прогноз и уровень риска;
- `src.service.app` поднимает FastAPI API с `/health` и `/predict`;
- `src.service.ui` поднимает Streamlit-интерфейс к той же модели;
- `src.service.ui_content` отделяет подсказки, демо-профили и dashboard-карточки
  от логики рендера интерфейса;
- `configs/.env.example` фиксирует параметры запуска сервиса без реальных
  секретов;
- `Dockerfile` собирает контейнер с FastAPI-сервисом, healthcheck и тестами
  внутри образа;
- `.dockerignore` исключает локальные окружения, кеши и внутренние метаданные из
  Docker build context;
- `SECURITY.md` фиксирует базовые решения по данным, секретам, API и
  зависимостям;
- `tests/` проверяет загрузку данных, инференс, API, шкалу риска, отсутствие
  внешних модельных зависимостей, контейнерные файлы и базовую логику UI.

Сервис пишет логи старта, остановки, ошибок и времени обработки `/predict`, а
`/health` показывает состояние модели. Ошибки инференса не передают клиенту
внутренние пути или stack trace: диагностические сведения остаются в логах,
внешний ответ остаётся нейтральным.
